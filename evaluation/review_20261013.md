## 核心能力为什么可以判定完成

### 两个 Agent 已独立承担职责

- `src/test_workflow/agents/test_generation.py` 完成一次生成或修订，通过 `adapters/agentdev.py` 复用旧生成、校验与候选保存能力，没有执行 pytest 或包办整个闭环。
- `src/test_workflow/agents/test_execution.py` 核对候选、调用真实执行工具、检查输入完整性并返回评估与路由建议，没有调用生成节点。
- 新 Workflow 没有把旧 `run_agent()` 整体包装成生成节点；生成与执行由新编排器显式调度。
- 执行 Agent 是规则决策与工具观察模式，符合原三页要求；课程没有要求每个 Agent 都调用大模型。演示时应准确说明其判断方式。

### 通信与状态管理有实际保护

- Message、AgentContext、AgentResult、ArtifactRef、ExecutionAssessment 等使用严格结构化契约。
- 节点读取序列化快照，返回受限状态补丁；WorkflowRunner 负责统一提交共享状态。
- 交接检查 run_id、轮次、节点、接收者、候选标识与产物摘要；防止跨任务串线、旧候选执行和重复消息消费。
- 保存 Context/Result、messages.jsonl、events.jsonl、状态快照，结论可关联回对应轮次和文件。
- 受控两轮集成测试明确检查执行反馈被消费，且反馈内容实际进入第二次生成上下文。

### 流程与错误处理超过最小顺序 MVP

- 具备顺序执行、条件路由、最多三轮反馈、无进展停止和历史候选选择。
- 无效候选进入评估但不执行；测试超时、模型错误、覆盖不可用、规格疑问和输入变化均不会报告为完成。
- 规格支持的源码缺陷保留失败断言，进入 `needs_review`，不会为了通过而弱化预期。
- 编排结束、测试结论、覆盖率和选中/最新候选分开报告。
- Windows 原子替换失败有有限重试；关键产物不能保存时不会宣称保存成功。
- CLI 与 Web 使用同一应用服务和正式 Workflow。

### 扩展与界面已经有可演示实现

- ResultSummaryNode 通过接口、注册和流程定义接入，作为通用尾部节点运行，无需加入该节点的业务特例。
- Web 支持任务提交、状态轮询、逐轮结果、事件、反馈、最终测试与报告下载，足够演示多 Agent 协作。
- 已有 wheel 安装后的 CLI、Web 静态资源与两轮反馈验证记录，因此不能再把“干净安装完全未实施”作为当前结论。

## 剩余差异与建议优先级

### 1. 同步文档与清单——交付前应处理

这是当前最确定、成本最低的收尾工作。

- `docs/scope.md:35` 仍写默认测试超时 30 秒，而当前配置、CLI、Web 和登记的 vendor 修改均以 60 秒作为默认值。
- `evaluation/verification.md:36` 的旧描述只列一个 vendor 修改；当前补丁清单为六项。应标明该段是当时记录，或补充清晰的当前修改说明，避免被理解为当前仅改一处。
- Design 开头、development 的阶段总结以及主清单 P7 复选框仍含“干净安装待实施”等旧状态，和后续已完成的安装记录不一致。
- 主清单多个总体完成标准、最终自检与可选界面条目没有勾选。应按实际证据更新已完成项；未实现的流程图和未做的实验保持未完成，不批量全勾。

保留 P0–P6 当时的测试数与运行事实是合理的；应增加统一的“当前状态”，不要把所有历史测试数改为 711，或把旧阶段的未改 vendor 结论改写成新的历史事实。

### 2. 源码单独输入——如果仍希望支持，需要补开发

此前讨论的方向是源码必填、规格选填，但当前实现仍明确要求非空规格：

- CLI `--spec` 为必填，见 `src/test_workflow/cli.py:31`。
- `create_run()` 固定进入 `OracleMode.SPECIFICATION`，见 `src/test_workflow/workflow.py:45`。
- 两个适配器都检查规格非空。
- Web 表单和 API 都要求规格，见 `src/test_workflow/web_static/index.html:10` 与 `src/test_workflow/web.py:31`。

因此不能仅删除前端 required 就声称支持。需要同时处理入口、状态初始化、节点门禁、Prompt、评估策略、报告与两种模式的验证。无规格时应使用现有行为测试模式，不能把模型根据实现猜出的规则当作独立需求证据。

这不是课程强制项；此前对话只是讨论可行性，并没有将该功能自动计作已实现。若不纳入本次提交，保持当前源码+规格范围即可。

### 3. 可选运行可视化——已有工作台，尚未完成计划中的图高亮

页面显示事件、消息和各轮指标，但没有固定 Workflow 图或节点进度高亮，因此 A.2 不能记为完成。服务进程重启后 Web 任务目录仍存在，但内存任务列表不会自动恢复；历史结果目前通过 CLI inspect 读取。

三页中的可视化编排界面属于可选项。现有工作台已经能够支持演示，不需要为交付临时加入拖拽编辑器或复杂调度。

### 4. 扩展性的结论应准确

`WorkflowRunner.run()` 检查前两个节点必须是 `test_generation`、`test_execution`，核心循环按固定语义处理候选与评估。现有扩展主要是替换已有接口实现和追加读取结果的尾部节点。

这足以体现课程 MVP 的可扩展设计，但新 Agent 若要改变业务结论、插入反馈环或调整核心顺序，需要正式扩展契约与路由。README/演示应使用“可扩展的测试工作流”，避免“任意 Agent、任意流程无需改代码”等超出实现的表述。
